Revised steps — new machine:
1. Copy the whole parent folder (all 3 sibling repos: soljet-postiz, catalyst-knowledge-graph, arboryx.ai) — or git clone each fresh, then manually copy over what git doesn't track:
     .env                                        (all secrets + the live Postiz/routing ids)
     data/posted_log.sqlite                      (what has already been posted — see 1b)
     auth/                                       (cloudflare.yaml: tunnel + CF API tokens; x.yaml: X app keys)
     products/arboryx.ai/handles.yaml            (live Postiz ids, gitignored)
     arboryx.ai/dev-utils/service_account.json   (GCP service-account key)
   Everything above is gitignored on purpose, so a `git clone` gives you NONE of it.
   Quickest check on the old machine: `git status --ignored --short | grep '^!!'`

1b. ***EXPORT THE POSTIZ DATABASE BEFORE TEARING THE OLD MACHINE DOWN.*** This is
    the one thing a git clone + .env does NOT give you: the Postgres volume holds
    the Integration table = every connected channel and its OAuth access/refresh
    tokens. Without it the new machine comes up with ZERO channels and you have to
    redo the X + LinkedIn OAuth dance by hand (painful — LinkedIn especially).
      OLD machine — one target does all of it (postgres alone is enough; it starts
      postgres if the stack is already down and stops it again afterwards):
        make postiz-export              # + UPLOADS=1 for the ~87M of media/avatars
      Writes to data/postiz_export/: the DB dump AND posted_log.sqlite (taken via
      the sqlite backup API, not cp, so a mid-write poster can't hand you a torn
      copy). Prints the Integration/Post/Media counts so you can see it worked.
      data/postiz_export/ is gitignored — it holds live OAuth tokens, so move it by
      hand (scp/USB), never commit or email it.

      WHAT THE DUMP ALREADY CONTAINS (it is the whole database, not just tokens —
      verified 2026-09-05: 69 tables): Integration (channels + OAuth tokens), Post
      (775 = the full publish history), Media (498), Notifications, Customer, Organization, and
      User — i.e. the Postiz LOGIN itself (email + bcrypt hash; bcrypt carries its
      own salt, so the same email/password works on the new box regardless of .env).
      `pg_dump -d <db>` covers exactly one database and never includes Postgres'
      own pg_catalog/information_schema, so "app data only, no system tables" is
      already what you get. Nothing further to export.

      REDIS: do NOT bother. Postiz uses it as an ephemeral BullMQ queue/cache —
      checked live, the volume held 1 key total and not even a Postiz one. Carrying
      stale queue state to a new machine risks ghost/duplicate jobs. Skip it.

      posted_log.sqlite (385 rows) is the POSTER's own record of which catalysts
      already went out. It is NOT in the Postiz DB, and it — not Postiz — is what
      stops the new machine re-posting everything from scratch. `make postiz-export`
      now bundles it for you, so step 1's copy of it is belt-and-braces.

1c. IMPORT on the NEW machine. Drop data/postiz_export/ in place (or pass FILE=),
    then:
        make postiz-import              # + UPLOADS=1 if you exported the media
        make deploy                     # then check the UI shows the channels
      No prior `make deploy` needed first — the dump carries the CREATE TABLE
      statements, so it restores into a bare postgres. With no FILE= it picks the
      newest postiz-db-*.sql in data/postiz_export/. It prints the restored
      channels and Post count at the end.

      The two ways this bites, both now guarded by the target itself:
      - The dump is --clean --if-exists: it DROPS what's there. If the target DB
        already has posts, postiz-import REFUSES rather than silently discarding
        whatever that machine published. Override with FORCE=1 only when you are
        certain that box is being replaced.
      - It won't overwrite a posted_log.sqlite that is LONGER than the incoming
        one (again FORCE=1 to insist), and keeps the previous file as a .bak.

      SPLIT-BRAIN, the part no target can save you from: never let both machines
      run the scheduler against the same channels. Two posted_log.sqlite files
      diverging means the same catalyst goes out twice, on live accounts. Pick ONE
      authoritative machine and `make tunnel-down` + `make down` on the other.

1d. Tearing the old machine down does NOT destroy any of this: `make down` and
    `make tunnel-down` only stop containers — the postgres/uploads volumes survive
    on disk (docker volume ls | grep soljet-postiz). You can always start postgres
    alone later and dump it. Only `docker compose down -v` / `docker volume rm`
    actually deletes the tokens.
2. Add to the new machine's ~/.bashrc: export GOOGLE_APPLICATION_CREDENTIALS="<new path to the key file>"
3. Fix any absolute paths (.env, that export) if the new machine's mount layout differs from WSL's /mnt/c/...
4. Install Docker + Compose
5. make deploy
6. make tunnel-up — starts cloudflared + the scheduler-trigger listener together (idempotent; do NOT use make scheduler-up, that also re-syncs GCP job configs via gcloud, unneeded and requires gcloud auth on the new box)
7. Nothing to touch on GCP — same tunnel hostname, jobs keep firing, now answered by the new machine
8. Verify: make heal-check, make post-status, make social-schedule, make tunnel-check (containers running + live healthz, local and public)

Note: trigger.arboryx.ai/run is authenticated (Bearer SCHEDULER_TRIGGER_TOKEN, constant-time compare) — confirmed live, no auth/wrong token both get 401. Only /healthz is open, and that's read-only. The token is in .env, copied over in step 1.

Bring this (old) machine down — don't use make scheduler-down, it calls gcloud scheduler jobs delete and removes the Cloudflare tunnel route (exactly what you don't want mid-migration):
make tunnel-down    # stops + removes cloudflared and scheduler-trigger together, local only — GCP jobs and the tunnel route are untouched
make down           # stops the rest (postiz, postgres, redis, temporal stack)
make down is interactive (asks y/N) and only stops containers — no cloud side effects, volumes preserved.

New: make tunnel-check verifies both pieces end to end (container running + live /healthz, checked both from inside the container and over the public hostname) — run it after tunnel-up on the new machine, and again after tunnel-down on the old one to confirm it's actually offline there.
